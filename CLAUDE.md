## Git workflow

- Work **only on branch `dev`**. Never commit to `main`. **Never push** and no force operations unless the user explicitly asks.
- Local commits are allowed once a roadmap step is finished and verified (`npm run build`, `npm run lint`, tests once they exist). Stage explicit paths, scan the staged diff for keys/tokens before committing, end commit messages with the `Co-Authored-By: Claude …` line the harness provides.

### API types (`src/shared/api/schema.d.ts`)

Generated by `openapi-typescript` from the backend's OpenAPI document and committed, so the build needs no running backend. Regenerate whenever an endpoint or DTO changes. Node does **not** trust the ASP.NET dev certificate (it ignores the macOS keychain, even after `dev-certs --trust`), so with the API running via `dotnet run` fetch the file first (`-k` is fine for localhost):

```bash
curl -ks https://localhost:7054/swagger/v1/swagger.json -o /tmp/openapi.json && npm run api:types -- /tmp/openapi.json
npm run api:types -- http://localhost:8080/swagger/v1/swagger.json   # docker compose (plain http), no curl needed
```

Use `components['schemas'][…]` for request/response shapes; never hand-copy a DTO. Since B11 the document is complete: every route has its 2xx body, all properties of response DTOs are required (a nullable one is `T | null`, never `?`), and a 400 is `ValidationProblemDetails` with `errors?: Record<string, string[]>` (field → messages). The server offers each JSON body under three media types (`text/plain`, `application/json`, `text/json`) — index with `'application/json'`. Request bodies stay lenient (`title?: string`): leaving a property out is part of the contract (default or cleared).

## State of the code

**The old UI is gone** (deleted step by step in F3–F9: `components/`, `containers/`, `pages/`, `services/`, `legacy.css`, the Gaegu/Beleriand fonts, the `dark` class bridge, `allowJs`, the ESLint JS block). Everything under `src/` is TypeScript; `src/app`, `src/features/*` and `src/shared/*` are the app.

**TypeScript (since F1):** `tsconfig.app.json` is `strict` (+ `noUncheckedIndexedAccess`, `verbatimModuleSyntax`). Imports use the `@/` alias for `src/` (declared in `tsconfig.app.json` *and* `vite.config.ts` — keep both in sync). Tests sit next to the code as `*.test.ts(x)`; Vitest does not expose globals, import `describe/it/expect` from `vitest`. New code must pass `npm run typecheck`, `npm run lint` and `npm run format:check`. The test timeout is 15 s (`vite.config.ts`): the autosave tests wait for the real 800 ms pause.

**Design system (since F2):** `src/shared/ui/theme.css` holds the tokens of `docs/DESIGN.md` in the backend repo (Tailwind 4 `@theme static`); `src/index.css` only imports Tailwind and the tokens; Tailwind's default palette is switched off (`--color-*: initial`), so a stray `bg-white` generates nothing. Rules for UI:
- **Use the role/ramp tokens, never `dark:` and never hex values.** `bg-bg`, `bg-surface`, `text-text`, `bg-accent`, `bg-accent-200 text-accent-800`, `bg-accent-2-*` (sage), `bg-neutral-*`, `bg-mood-great|good|okay|low|rough` + `text-on-mood-*`, `bg-miss`, `border-divider`, `rounded-card`, `shadow-sm|md|lg`, `font-display` (Caprasimo), `text-page|dialog|card|kicker`. The dark ramps are the light ones mirrored, so one set of classes serves both themes. Spacing is 1.10× (`p-1` = 4.4 px).
- Theme = `data-theme` on `<html>` via `src/shared/lib/theme.ts` (`getInitialTheme`/`applyTheme`/`storeTheme`; stored choice → system preference → light). The shared React context is `ThemeProvider` / `useTheme()` (`@/shared/ui`); only a choice the person makes is stored.
- Components in `@/shared/ui` (barrel): `Button`/`IconButton`, `Tag`, `Card`, `Checkbox` (a real checkbox drawn as a rounded square or circle), `Field` + `Input`/`Textarea`, `Dialog` (native `<dialog>`, controlled), `Select` (a pill-shaped native `<select>`), `Slider`, `ThemeSwitch`, `ProgressDonut`, `PageHeader`, `Spinner`, `Skeleton` + `SkeletonGroup`, `FormMessage` (the `role="alert"` text for a whole form), `ThemeProvider` + `useTheme`, `ToastProvider` + `useToast`. Real `button`/`input` elements only, every icon-only control needs a `label`. Icons are Lucide (`LucideProvider` in `main.tsx` sets stroke 2.75). `cn()` joins class names (no tailwind-merge: pass `className` for layout only, not to override a component's own colours).
- `Field` passes its a11y props to the control as a render prop: `<Field label error>{(c) => <Input {...c} {...register('x')} />}</Field>`.
- Tests: jsdom has no `<dialog>.showModal` and no `matchMedia` (both stubbed in `src/test/setup.ts`; the `matchMedia` stand-in says "not dark" — inject your own where it matters, see `systemTheme`).

## Start-up, shell and delivery (since F9)

- **`main.tsx` checks the configuration before it loads the app.** `apiUrlProblem(VITE_API_URL)` (`shared/api/apiUrl.ts`, pure) → a bad or missing address renders `StartupError` (design system only: no router, session or API client, those are what may be missing) and the app is never imported; otherwise `app/start.tsx` is imported on demand (its API client refuses to exist without a valid address). A chunk that fails to load gets its own message. A path such as `/api` is a valid address (API behind the same server).
- **The shell is one element with two layouts** (`app/Sidebar.tsx`, `AppShell.tsx`): from `lg` the floating sidebar of the design; below it a slim top bar (logo circle, theme switch, log out) and a navigation bar `fixed` to the bottom (icon over label, current = `accent-200`/`accent-800`, because `bg` on `accent` is 3.0 : 1). Same DOM, only classes differ - one tab order, one "Main" landmark, and jsdom tests see everything. The name/email card is desktop only. `AppShell` has a "Skip to content" link and moves the focus to `<main>` when the person goes to another *screen* (first path segment), not when they page through days/months.
- **Tab titles:** `PageHeader` sets `document.title` ("<title> · <kicker> · Hanna's Habits") through `useDocumentTitle`; the login page does it for log in / create account. Don't render a second `PageHeader` per screen.
- **Loading = `Skeleton`/`SkeletonGroup`** (grey blocks in the shape of the content, announced once as a `status`); a spinner only inside a dialog and for the page-level "restoring the session". Errors: `RouteError` (`errorElement` of a pathless route inside the shell, so a crashing screen keeps the sidebar); data that is there wins over a failed refresh (see the screens).
- **`useToday()`** (`shared/lib/useToday.ts`) instead of `new Date()` read while rendering, for anything that *describes the present* (highlighted day, days left, the streak's `asOf`): it renders again at local midnight (timer) and when the tab/window comes back (timers are frozen in the background). A date the person *acts on* (a new habit's start day) is read in the handler; the diary day comes from the address.
- **`vite.config.ts` `manualChunks`:** `react` / `forms` / `vendor` / the app, so a deploy that only changes the app keeps the libraries cached (nginx caches hashed files as immutable). No chunk is over 500 kB.
- **Docker/nginx:** `nginx/default.conf` + `nginx/security-headers.conf` (included in every location that sets headers of its own - `add_header` is not inherited otherwise): nosniff, `X-Frame-Options`, referrer and permissions policy, `frame-ancestors 'none'`; a missing file with an extension is a 404 (not `index.html`); `/healthz`; `HEALTHCHECK`; the build fails when `VITE_API_URL` is empty. No HSTS (TLS ends at the proxy) and no full CSP (it would have to name the API origin and Google's scripts; untestable without a browser and a wrong one breaks the login silently).
- Look at it, then trust it: **none of the F9 layout work has been looked at in a browser** (small-screen bar, bottom navigation, the habit grid on a phone).

## Talking to the API (since F3)

- `import { api } from '@/shared/api'` and call by the routes of the OpenAPI document: `await api.get('/api/habits/{id}', { path: { id } })`, `await api.put('/api/daily-diaries/{date}', { path: { date }, body })`. The route, the path/query parameters, the body and the answer are checked against `schema.d.ts` (`204` → `void`); a renamed route or changed DTO breaks `npm run typecheck`. DTO types: `Schema<'HabitOverviewDto'>`, never hand-copied. Dates in `path`/`query`/`body` are the `yyyy-MM-dd` strings (see below).
- Every failure is an **`ApiError`** (`status`, `title`, `detail`, `fieldErrors` per field, `isNetworkError` for status 0). `errorMessage(error, fallback)` is the text for a person. A cancelled request stays a cancellation. Services/hooks do not catch and swallow; the component decides what to show.
- Server data goes through **TanStack Query** (`useQuery` / `useMutation` in a hook next to the feature's API calls). Query keys start with the feature, then the parameters: `['habits', 'overview', { from, to }]`. A 4xx is not retried (`src/app/queryClient.ts`), writes never are. The cache is cleared when the person changes or leaves (`AuthProvider`).
- The auth endpoints (`login`, `register`, `google`, `refresh`, `revoke`) use a **client without token logic** (`authApi` in `features/auth/authClient.ts`): a 401 from `login` means "wrong password" and must not start a refresh. `authGateway.ts` holds the calls that start a session (`login`, `register`, `google`), `sessionGateway.ts` the two the session itself makes (`refresh`, `revoke`) — separate interfaces, because the session must not depend on how a person signs in.
- Tests: `fakeServer` + `createHttpClient({ adapter })` for code that talks to the API, `fakeSession()` for components that need a signed-in person; no mocking library. For forms use `ApiError.fieldErrors` → `setError`.

## The login screen (`src/features/auth`, since F4)

`LoginPage` = hero + one card with a login/register toggle (the toggle button stays the same element, so the focus survives). It only collects and sends (`useAuthentication` → `useMutation` per way of signing in → `signIn(result)`); it does **not** navigate: the `PublicOnly` guard sends a signed-in person to `location.state.from` (set by `RequireAuth`; only an in-app path is followed) or `/`. The server's texts for 401 (wrong credentials), 429 (locked out) and Google's 409 (a password account owns the email) are shown as they are; a register 409 goes under the email field. `LoginPage` takes `gateway` and `GoogleButton` as optional props (the real ones by default) so tests run it without a network or Google's iframe.

Google: `GoogleSection` uses Google's own `GoogleLogin` button (ID-token flow → `credential` → `POST /api/auth/google { idToken }`); a custom-styled button would need `useGoogleLogin`, whose popup flow yields an *access* token, not the ID token the backend verifies. Google's button can be pill-shaped and light/dark, not restyled further. Its width follows its slot (`googleButtonWidth`: 200–400 px, 320 until measured; `useElementWidth` with a `ResizeObserver`). The server's password rules come back as one message with a line per rule (`applyServerError` joins with `\n`, `Field` keeps the breaks). Empty `VITE_GOOGLE_CLIENT_ID` = no Google part at all. The app's origin must be an authorised JavaScript origin of that client in the Google Cloud Console.

## The habits screen (`src/features/habits`, since F5)

`HabitsPage` = the month tracker (DESIGN.md §4.3) fed by **one** `GET /api/habits/overview` (`from`/`to` = the month, `asOf` = the client's today). It takes a `gateway` prop (`habitsGateway` by default; tests pass `fakeHabits(...).gateway` from `src/test`, an in-memory stand-in with `hold()` / `failNext()`). The month lives in the address (`?month=2026-09`, none = current month, nonsense = current month; `months.ts`). The rules sit in small pure modules, each with a table test:
- `cells.ts` `cellState`: before `startDate` = not applicable (never "missed"); a day that is not in the overview's **`scheduledDates`** is hidden as "not scheduled" (the server keeps a record there but it is neither shown nor counted); otherwise done / missed / due today / upcoming. **The client never works out "is it due" from a rule** (since F11): the rule - weekdays, every N weeks, every N days, monthly on a weekday or a date - is evaluated once, in the backend's Domain, and arrives as the list of due days of the requested range (`HabitGrid` and `TodayHabitsCard` pass `scheduled: scheduledDates.includes(day)`). Only done, missed and today's cells toggle (`isToggleable`) - the server would accept marks on future or unscheduled days, so this is the one place that blocks them.
- `weekdays.ts`: the API's days are `0 = Sunday`, the UI is Monday first (`MONDAY_FIRST`); `scheduleLabel` = "Every day / Weekdays / Weekends / Mon · Wed · Fri" (the label of a weekly rule that repeats every week).
- **The rule (since F11):** `recurrenceSchema.ts` is the form's model of `recurrence` - flat like the API's object, with the facts of *every* kind kept (switching kind and back loses nothing; numbers are `null` while a field is empty), limits mirroring `HabitSchedule`, checks on the object so that only the chosen kind's facts are validated (a hidden field must never block the form). `recurrence.ts` converts: `toRecurrenceValues` (answer → form), `toRecurrenceRequest` (form → request: only the chosen kind's facts; an anchor only when there is one and the rule counts from a day), `sameRecurrence`, and says it in words: `recurrenceLabel` (the line under a habit's name: "Every 2nd week on Mon and Thu", "Last Saturday of the month", "On the 15th of the month", "Last day of the month" for 31) and `recurrenceSummary` (the form's sentence, adds where a rhythm counts from). The `anchor` is part of the rule, not the start date: it is `null` in the form while the rhythm follows the start date (then the field "Counted from" shows the start date and nothing is sent), and an edit sends back the one the habit already has, so moving the start date never shifts the rhythm.
- `RecurrencePicker` (the "Repeat" select + only what the kind needs, `WeekdayToggle` for weekly) is controlled and knows nothing of forms/servers; `HabitForm` hands it the messages. The server's one `recurrence.interval` is mapped to the weeks or the days field by `applyServerError`'s `aliases`. In an edit (`editing`) a *changed* rule shows the note that it re-judges past days (DESIGN.md §9). The submit label keeps "· N×/week" only for a weekly rule that repeats every week.
- Ticking (`useMarkHabit` in `habitMutations.ts`) is optimistic and **serial**: every mark shares one mutation `scope`, so a PUT and a DELETE for one cell cannot overtake each other; a failure writes the *inverse* into the cache (not a snapshot - that would also undo later ticks - and it is the only repair when the refresh fails too); the overview (the streak is the server's rule) is fetched again once, when the last pending mark has settled. The gateway reads a 404 on `unmark` as success (the day is not marked, which is what was asked). `overviewCache.ts` writes a change into every loaded overview whose range covers the day (the diary's "today" panel will have its own range).
- One `HabitForm` (RHF + zod) serves add and edit. The edit dialog loads `GET /api/habits/{id}` and never from the cache (`gcTime: 0`): the overview has no description and `PUT` writes the whole habit. `startDate` is a field of the form (`Starts on`): the client's local today on create, changeable on edit (F10) - an earlier day makes earlier days tickable, a later one hides the marks before it (they are kept). The optional note (`description`, ≤ 500) is in the form but shown nowhere else (decision in F5).
- **Quota rules (since F13, "N times a week / month"):** `timesPerWeek` (1..7) and `timesPerMonth` (1..28) have **no due day**: the server lists every day from the start in `scheduledDates` ("can be ticked") and `quotaPeriods: [{ from, to, done }]` says how far each calendar week (Monday-Sunday) / month has come, counted over the whole period. `quota.ts` only tells the kinds apart (`isQuota`, `streakUnit`) and words the progress (`quotaProgressText`: "2 of 3 this week", "in that week" for another week) - the number is the server's. `cellState({ quota })` has no "missed" and no "due today": an unticked past day or today is **`open`** (an empty ring like a day to come, but tickable). The line under the name is "3 times a week · 2 of 3 this week" (progress only when today's period is in the answer, i.e. the month on screen has it). `StreakBadge` takes a `unit`: a quota's streak is weeks / months ("3wk", aria "Current streak: 3 weeks"). `withCompletion` moves the `done` of the day's period along, so the number changes with the tick; the server's own count replaces it on the refetch. The form: one `times` field (kept when the kind switches, limited by the chosen kind), the submit label says "· 3×/week" / "· 8×/month", the server's `recurrence.times` lands under it. The legend gets "Not done (any day counts)" only while a quota habit is on screen.
- Data that is there wins over `isError`: a refresh that fails must not wipe the grid.

## Parts of a habit - sub-habits (`src/features/habits`, since F14)

A habit can have up to 10 *parts* ("Legs" and "Arms" of "Sport"), each planned on some of the habit's own weekdays and ticked on its own. The server's rules (DESIGN.md §5): a part is **due** where the habit is due *and* the weekday is one of the part's; the habit's day follows its due parts (all done = done); ticking the habit ticks the parts that are due that day, un-ticking it clears all part ticks of the day.
- **`subHabits.ts`** (pure): `dueSubHabits` / `subHabitProgress` only *look up* the per-part `scheduledDates` / `completedDates` the server sends - no due rule on the client, as for the habit's own cells. `habitWeekdays(recurrence)` is the one **copy of a server rule**: the days a part may choose (weekly: the chosen days, "the last Saturday": that weekday, any other rule: all seven). It only hides choices; the server's 400 stays the authority (a real-API check ran every rule kind against it). `strandedWeekdays` = days a part has that the habit has not (any more): never due, and said so in the dialog.
- **In the grid:** under a due day's cell `PartsButton` shows "1/2" and opens `DayPartsDialog` (`SubHabitChecklist`: the day's due parts, ticked one by one; a day to come is read-only, a done part can always be taken back). The cell itself still ticks the whole day - which ticks every due part. A row's "Parts of ..." icon button opens `SubHabitsDialog`; the line under the name ends with "· N parts"; the legend explains "1/2" only while a habit has parts. The same `SubHabitChecklist` sits under a habit in the diary's Today card. **Parts as rows:** a habit with parts has a chevron button ("Show / Hide parts of X", `aria-expanded`) first among its icon buttons; open, `PartRow` shows one row per part under it - the part's own due days (`scheduledDates`), its own ticks (`useMarkSubHabit`, the same mutation as the dialog), no streak - and the "1/2" under the habit's cells is left out. The set of open habits is state of `HabitsPage` (the grid is replaced by a skeleton while a month loads, so state in the grid or row would be lost on a month change); it is not persisted.
- **`SubHabitsDialog`** (add / change / remove; `SubHabitForm`, RHF + `subHabitSchema`) is a dialog of its own, not a section of the habit's form, on purpose: every step is saved at once, while the habit form has a Save button; a form inside a form is invalid HTML; and a part is checked against the habit's *saved* rule, not a half-edited one. A habit without parts opens straight on the form. `WeekdayToggle` takes `allowed` (days that can be switched *on*; one that is on already can still be switched off - how a stranded day goes), `legend` and `presets`.
- **Ticks** (`habitMutations.ts`): `useMarkSubHabit` shares the mutation key and the serial `scope` of `useMarkHabit` - a habit's tick and a part's tick of one day change each other's result, so they queue together - and its single refresh after the last pending mark; a failure writes the inverse part tick (which takes the habit's day along). `overviewCache.ts`: `withCompletion` writes the cascade into the parts, `withSubHabitCompletion` completes / takes back the habit's day (not at all for a day the part is not due on) - the optimistic mirror of a server rule; checked against the real API (every change equals what the server then says), and the refetch repairs anything else. Adding, changing and removing a part are not optimistic: they refresh every view (`habitKeys.all`) and the dialog reads the habit from the overview.
- Tests: `fakeHabits({ subHabits })` keeps the server's rules (limit 10, a title once per habit ignoring case, days of the habit only - checked only where they change -, the due rule, the cascade), pinned by `src/test/fakeHabits.parts.test.ts`; `HabitsPage.parts.test.tsx` runs both dialogs through the page.
- Not built: reordering parts, parts in the create dialog (a habit has to exist first), a quota-style "N of the parts". The statistic over the parts - and a streak per part - is the next section.

### Notes on a part's day (since F18)

A free-text note belongs to **one part on one day** (`SubHabitOverview.notes: { date, text }[]`, one per day, ≤ 500 characters, independent of the tick and of the plan; DESIGN.md §4.3 and §5). *Written* in the part's own row (see "Parts as rows"), *read* on the habit's own cell.
- **`shared/ui/HoverCard`** - the app's own card beside a trigger (`label`, `card`, children): opens after the mouse has rested 250 ms, closes 150 ms after it left trigger *and* card (so the pointer can cross the gap), opens on keyboard focus, stays while a field in it has the focus, Escape closes it and gives the focus back, scrolling / resizing closes it. `position: fixed` (the grid's scrolling box cannot clip it) and rendered right after its trigger (tab order: cell → field → next cell). A touch never opens it; a mouse *press* does not count as a request for the card (the press is tracked, `:focus-visible` was not reliable).
- **`NoteEditor`** (the card on a part's cell) autosaves: 700 ms after the last key, on blur, on unmount; the trimmed text, `null` for an empty field (= take away); only a change is written. It holds its own draft - a refresh does not replace what is being typed. **`DayNotesTip`** (the card on the habit's cell) lists `notedPartsOnDay` - only the parts that have a note that day, by name, the note under each; a day without any note has no card at all.
- **Which cell opens what** (`HabitGrid`): a part's cell opens the editor unless the day is before the habit's start, or is not the part's day *and* has no note; the habit's cell opens the tip when `notedPartsOnDay` is not empty. `DayCell` gets a `note` (a dark dot in its corner, and ". Note: …" after its name for a screen reader).
- **`useSaveSubHabitNote`**: optimistic (`withSubHabitNote`), one serial `scope` for all note writes (an older text must not overtake a newer one), a failure toasts and asks the server again (no inverse of a text). Gateway: `setSubHabitNote` (PUT), `clearSubHabitNote` (DELETE; a 404 is "gone already").
- Tests: `fakeHabits({ subHabits: [{ notes }] })` keeps the server's rules (trimmed, blank / too long = 400 on `text`, independent of ticks, gone with the part); the editor's tests wait out the real 700 ms pause - **vitest's fake timers hang Testing Library's async helpers** (its `asyncWrapper` only advances Jest's). Checked against the real API (round trip, 400 keys, optimistic cache = server).
- Not built: a touch route (the day's dialog would be the place for a field per part), notes in the diary's Today card or the statistics, history.

## The statistics screen (`src/features/statistics`, since F15)

`StatisticsPage` = `/statistics?month=2026-10` (DESIGN.md §4.6): per habit what was planned and done in the month, when it was last done, its streak and longest streak, and the same per part. **One** request, `GET /api/habits/statistics` (`from`/`to` = the month, `asOf` = the client's today); **every number is the server's** (the rule is the backend Domain's `HabitStatistics`, next to the streak's) - this feature only words it. It takes a `gateway` prop (`fakeHabits(...).gateway` in tests).

## The diary screen (`src/features/diary`, since F6)

`DiaryPage` = `/diary/:date` (DESIGN.md §4.2). The date is the key - no ids: `GET/PUT /api/daily-diaries/{date}`. A date that is not a real `yyyy-MM-dd` day redirects to today; the 404 of a day without an entry is `null` in `diaryGateway.load` and shows the empty form. It takes `gateway` and `habitsGateway` props (tests pass `fakeDiary(...)` / `fakeHabits(...)` from `src/test`, both with `hold()` / `failNext()`).
- **Autosave, no save button.** `createAutosaver` (`autosave.ts`, plain TypeScript, tested with fake timers) debounces (`SAVE_DELAY_MS` = 800), writes the **whole** document, allows **one request in flight** (changes meanwhile only replace the waiting value; one follow-up carries the newest, after its own pause unless that is over already), and keeps a failed value (`error`, no automatic retry; `flush()` = the "Try again" button; the next change sends it in full anyway). A failure made good by a newer change is not reported. `useDayAutosave` puts it into React (`useSyncExternalStore`), toasts a failure, flushes when the tab is hidden and asks the browser's "leave this page?" only while something is unwritten.
- **The draft is React state, the query cache is its memory.** `DiaryEditor` (one per day, `key={date}`) keeps the draft in `useState` (a controlled input must update in the keystroke's tick; the query cache notifies asynchronously and the caret would jump). On leaving the day (another date, another screen) the cleanup writes the draft into the query cache - **only if the entry still exists** (after a log-out the cache is emptied and the text of the person who left must not come back) - and flushes at once. `useDiaryDay` has `staleTime: Infinity`: the cached day is never refetched behind the person's back, because it can be newer than the server's copy while a write is on its way. It lives the default five minutes after leaving.
- **Two editors of one day** (leave and come back while the last write is still going): `diaryGateway.save` queues writes **per date**, so an older write cannot land after a newer one.
- **The model** (`diaryDraft.ts`): the server's document with text never `null` and an `id` on every list row (React keys; never sent). `toRequest` sends the whole day with explicit `null`/`[]`, trims, and leaves blank lines out (the server answers 400 for a blank list entry); an all-empty day is a `PUT` the server turns into a delete. Limits (`DIARY_LIMITS`) mirror the backend's and sit on the inputs as `maxLength`, so a save is not refused for length.
- **"Not set" is a state.** Mood, body and mind can be `null` (a day may be just a highlight): the sliders rest dimmed at the middle and show a dash, and mood, body and mind each have a small clear button (a radio group cannot be un-chosen by itself) - without them a day could never become empty again. `moods.ts` is the one list of mood number / label / icon / colour (the calendar uses it through the feature's `index.ts`).
- Lists (`EntryList`, `TaskList`) edit in place (`EditableLine`); a row left blank is removed on blur; the add row (`AddItemInput`) adds on Enter **and on blur**, because a typed line must not be lost to a missing Enter.
- **"Today's habits"** is `TodayHabitsCard`, owned by the **habits** feature (the diary imports only that and `HabitsGateway` from `@/features/habits`): overview with `from = to = date`, the same `cellState` rule as the grid, `useMarkHabit` shared with it, the streak as of the real today.

`CalendarPage` = `/calendar` (DESIGN.md §4.4): twelve month cards, every day with an entry in the colour of its mood, a click opens `/diary/:date`. **One** request feeds it: `GET /api/daily-diaries?from=&to=` (the year) → `[{ date, mood }]`. The list is a read of the *diary* resource, so it lives in the diary feature (`DiaryGateway.days`, `useDiaryDays`, `diaryKeys.days`) and the calendar imports it - with `MOODS` and the types - from `@/features/diary` (the diary never imports the calendar). ## The resolutions screen (`src/features/resolutions`, since F8)

`ResolutionsPage` = `/resolutions` (DESIGN.md §4.5): the year's numbered list (add, mark kept, edit, delete) and a card with how far the year has come. It takes `gateway` and `habits` props (tests pass `fakeResolutions(items, habitTitles)` and `fakeHabits(...)` from `src/test`; `fakeResolutions` resolves a habit link to the habit's *current* title, drops the link of a habit that is gone like the database's `ON DELETE SET NULL`, and answers 400 `habitId` for one that never existed).
- **The year is in the address** (`?year=2027`, none or nonsense = the current year; `years.ts` has the server's bounds 2000–2100, the parse is `shared/lib/years.ts` which the calendar uses with other bounds). Unlike the calendar it may look ahead: next year's resolutions are made in advance. The add row has `key={year}`, so a half-typed line does not move to another year.
- **The list is always asked again when the screen opens** (`staleTime: 0`, the cached copy shows meanwhile): every item carries the *title* of the habit it is tracked by, and a habit is renamed or deleted on a screen that must not know about this one.
- **Item writes go through one serial queue** (`scope: 'resolution-writes'`, shared by the kept toggle, the edit dialog and delete): `PUT` replaces the whole item, so two writes that overtook each other would leave the older state behind. The kept toggle (`useToggleKept`) is optimistic like ticking a habit: rollback by the *inverse* (not a snapshot), one refresh when the last pending write has settled. The edit dialog is **not** optimistic and sends `kept` as the list holds it *now* (a "Mark kept" click a moment ago is already in the cache). The dialogs are addressed by the item's id and look it up in the list on every render, so they close by themselves when the item is gone.
- **The add row** adds on Enter or the plus button, **not on blur** (unlike the diary this is not an autosaved document - nothing may be created behind the person's back). The text stays after a refusal (`errors.title`, or the 400 `detail` "at most 50"); at 50 items the row is replaced by a sentence. Linking a habit is only possible in the edit dialog (the design has no place for it at creation).
- **`HabitPicker`** is a `Select` of the person's habits (`useHabitList` / `GET /api/habits`, exported by the habits feature) with "No habit" first. The item's current habit is **always an option**, even before the list arrives or when the list does not have it - otherwise a form starting on a link would show "No habit" and drop the link on save. A failed habit list shows its message with "Try again" and the rest of the form still works.
- **`yearProgress.ts`** (pure, table-tested in four time zones): today counts as behind - day 280 of 365 is 77 % with 85 days left, the numbers of the mockup; a past year is 100 %, a year to come 0 % ("2027 has not begun yet"); a leap year has 366 days. `describeYear` builds the two lines of the card ("3 of 5 resolutions kept so far — 85 days left.", singular/plural, "this is the last day").
- The number circle of a kept item is **sage-700**, not the design's `accent-2`: the number on `accent-2` is 3.14 : 1 in the light theme, on sage-700 5.43 : 1 (DESIGN.md §8). "Kept" is a real button that takes it back; both buttons carry the item's title in screen-reader-only text, because a list of identical "Mark kept" buttons is not navigable.

## The session (`src/features/auth`, since F3)

Plain TypeScript in `session.ts`, put into React by `AuthProvider` (`useAuth()` → `status`, `user`, `signIn(result)`, `signOut()`; `useUser()` behind the login). Access token in memory, refresh token in `localStorage['hh-refresh-token']` (memory fallback if storage is blocked). **Never call the refresh endpoint outside the session.** Rules it keeps, each with a test:
- A refresh token works **exactly once**; a second use ends every session of the person. Parallel 401s share one refresh (`singleFlight`), and refreshes are serialised across tabs with a Web Lock (`crossTabExclusive`); inside the lock the newest stored token is read.
- Only a 400/401 answer ends the session (`endedBy: 'expired'` → toast). No network does not: the person stays signed in. On page load that case is the status **`unreachable`** (not `anonymous`): `RequireAuth` and `PublicOnly` show `ServerUnreachable` ("You are still signed in"), its "Try again" calls `reconnect()` = `session.restore()` again (allowed in that status only), and the `online` event does it by itself (`AuthProvider`).
- A **log-out in another tab** signs this one out at once: the token store listens to the `storage` event (`onRemovedElsewhere`; removal or `clear()`, not a rotation, only `localStorage`), the session drops with `endedBy: 'signed-out'` (no toast).
- After a reload `session.restore()` trades the stored refresh token for user + tokens (no `/me`). Log-out is local first, then `revoke` (which needs a valid access token — if it ran out, the tokens are traded first so the *current* refresh token is revoked).
- After sign-in call `signIn(authResult)` with the server's answer; `RequireAuth` sends anybody else to `/login` with `state.from`.

## Conventions to keep

- Dates are `yyyy-MM-dd` strings, never `toISOString()` (it is UTC and can be a day off): use `toApiDate` / `parseApiDate` from `@/shared/lib/dates`. Send the client's local today as `asOf` / `startDate`.
- Forms (since F4): **React Hook Form + zod** (`@hookform/resolvers`); Formik + Yup are gone. Pattern, see `features/auth/LoginForm.tsx`: the zod schema sits next to the feature (`credentials.ts`; limits mirror the backend's, the server stays the authority — do not copy its rules, e.g. the password policy, show its answer), `useForm({ resolver: zodResolver(schema) })`, `<form noValidate>` (our messages, not the browser's), `<Field>{(control) => <Input {...control} {...register('x')} />}</Field>`. A failed submit goes through `applyServerError(error, setError, FIELDS)` (`@/shared/lib/formErrors`): complaints the server pinned to a field (`errors.<camelCase>`) appear under that input and the first gets focus, everything else comes back as the text for a `<FormMessage>` (`role="alert"`) over the submit button. The submit calls a mutation (`useMutation`) and rejects with the `ApiError`.
- One shared axios client (`@/shared/api`); the 401 → refresh → retry is single-flight inside the session (see above).
- Services throw; components decide what to show. No `console.*` left in committed code.
